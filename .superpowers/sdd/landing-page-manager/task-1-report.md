## Migration command result

`npx prisma migrate dev --name add_landing_page` **could not be used.** Two blockers:

1. **`DATABASE_URL` points at the Supabase pgbouncer transaction pooler (port 6543).**
   Prisma's schema engine takes a session-level advisory lock, which transaction-mode
   pgbouncer does not support, so every `prisma migrate` invocation hung indefinitely
   (`migrate status`, `migrate dev`, `migrate dev --create-only`, `migrate deploy` all
   hung; several orphaned `schema-engine-darwin-arm64 ... can-connect-to-database`
   processes were left behind and had to be killed).
   **Workaround:** ran migrate commands with `DATABASE_URL` rewritten to the *session*
   pooler (`:6543` -> `:5432`, `&pgbouncer=true` removed). This worked immediately.
   The committed `.env` was **not** modified.

2. **The database had no `_prisma_migrations` table at all.** The existing schema
   (`User`, `Category`, `Post`, `Project`, `SEO` in schema `portfolio`) had been created
   with `prisma db push`, so the baseline migration `20250428092045_` was recorded as
   *not applied*. Running `prisma migrate dev` in that state makes Prisma detect drift
   and offer to **reset the database** — data loss on a live Supabase DB. That was not
   authorized, so it was avoided.

**What was run instead (non-destructive equivalent):**

```
# 1. Generate the SQL with Prisma itself (no shadow DB needed)
npx prisma migrate diff --from-schema-datasource lib/prisma/schema.prisma \
                        --to-schema-datamodel  lib/prisma/schema.prisma --script
#    -> only diff was CreateTable LandingPage + unique index on slug

# 2. Baseline the pre-existing schema
npx prisma migrate resolve --applied 20250428092045_
#    -> "Migration 20250428092045_ marked as applied."

# 3. Apply the new migration
npx prisma migrate deploy
#    -> "Applying migration `20260819134950_add_landing_page`"
#    -> "All migrations have been successfully applied."
```

### Bug fixed: previous migration was in the wrong place and targeted the wrong schema

A concurrently-running agent had already committed (`781d95a`) a **hand-written**
migration at `prisma/migrations/20260819134950_add_landing_page/migration.sql`.
That file was wrong twice over:

- **Wrong directory.** `package.json#prisma.schema` is `./lib/prisma/schema.prisma`, so
  Prisma reads migrations from `lib/prisma/migrations/`. It never saw the root-level
  `prisma/migrations/` copy (`prisma migrate status` reported only 1 migration).
- **Wrong schema.** It used `CREATE TABLE "public"."LandingPage"`, but every other table
  lives in the `portfolio` schema (`?schema=portfolio` in `DATABASE_URL`). It would have
  created an orphan table in `public` that the Prisma client never reads.

The misplaced file was removed via `git rm` (that staged deletion was swept into
concurrent commit `66c24d3`) and replaced with the correct file above.

## Errors / risks encountered

1. **`prisma migrate` hangs on the pgbouncer port (6543).** Any future migration work
   must use the session pooler (5432). Recommend adding to `schema.prisma`:
   ```prisma
   datasource db {
     provider  = "postgresql"
     url       = env("DATABASE_URL")
     directUrl = env("DIRECT_URL")   // session pooler, port 5432
   }
   ```
   and a `DIRECT_URL` entry in `.env`. Not done here — out of scope for Task 1.

2. **`migrate dev` would have offered to reset the live database.** Baselining with
   `migrate resolve --applied` avoided that. The DB now has proper migration history,
   so future `migrate dev` runs should behave normally.

3. **Multiple agents were operating on the same working tree concurrently.** Observed
   consequences: a duplicate/incorrect migration committed, my staged deletion absorbed
   into someone else's commit (`66c24d3`), and `node_modules` broken mid-task.
   **`npm install` was run in a pnpm project**, producing a stray `package-lock.json`
   (currently untracked) alongside `pnpm-lock.yaml`. This should be cleaned up and
   dependencies reinstalled with `pnpm install`.

4. `lib/prisma/schema.prisma` has no trailing newline (pre-existing; left as-is).
